\section*{Introduction}

In this assignment we worked with the Porto Taxi Trajectory dataset:
1.7 million taxi trips from July 2013 to June 2014, where each trip has a
GPS point every 15 seconds. We first explored and cleaned the data, then
designed a MySQL schema and loaded the cleaned data into it, and finally
answered ten questions with SQL and Python.

The main problems we had to solve were that TRIP\_ID is not unique, that
some trips have almost no GPS points or obviously wrong points, and that
83 million GPS points take a lot of space and time to load.

The first days we sat together at school, went through the assignment and
agreed on a plan for the EDA, the cleaning, the schema and each query. After
that Ingrid took over and did most of the EDA, the loading and the queries on
her own. The parts she got stuck on she handed over to Olav, who continued
from there. Whenever one of us did not understand something in the other's
work, we sat down and worked it out together.

MySQL 8.0 ran locally in Docker, and we used Python with
\texttt{mysql-connector-python}, \texttt{pandas} and \texttt{haversine}.

Repository: \url{https://github.com/olavhalleraker/tdt4225-project}

\section*{Results}

\subsection*{Part 1 -- Exploratory data analysis}

The raw CSV has \textbf{1,710,670 trips}, \textbf{83,409,386 GPS points}
and \textbf{448 taxis}, covering exactly one year.

\textbf{Metadata.}
\begin{itemize}
  \item ORIGIN\_CALL and ORIGIN\_STAND are the only columns with empty values
        (78.7\,\% and 52.9\,\%). This is expected, since they only apply to
        call type A and B. 11,302 B trips still have no stand.
  \item TRIP\_ID is just TIMESTAMP + ``6'' + TAXI\_ID. 80 IDs occur more than
        once, and in most cases the copies are different trips, typically
        a short stub next to the real one.
  \item Call types: A 21.3\,\%, B 47.8\,\%, C 30.9\,\%.
  \item DAY\_TYPE is ``A'' in every row, and MISSING\_DATA is true for only
        10 rows. Neither column tells us anything useful.
  \item TIMESTAMP is in UTC. 157,929 trips end up in a different time band
        depending on whether we use UTC or Porto time, so we use local Porto
        time (Europe/Lisbon) everywhere.
\end{itemize}

\textbf{Trajectories.}
\begin{itemize}
  \item Median 41 points per trip. 43,904 trips (2.6\,\%) have fewer than
        3 points: 5,901 are empty, 30,609 have one point and 7,394 have two.
  \item Median duration is 10 minutes and median distance 4.0\,km, but the
        longest trip is 16\,h and the longest distance 1,229\,km.
  \item 32 trips have points far outside Portugal, as far away as latitude 51
        and longitude 53. These are GPS errors.
  \item 38,216 trips have at least one jump of more than 833\,m in 15\,s
        (above 200\,km/h). Most of them look like a gap in the signal rather
        than a single bad point, and they explain the extreme distances.
  \item 7,142 trips leave the Porto area, but these are mostly real trips
        on the motorway, so we kept them.
\end{itemize}

\edafig{polyline_points_per_trip}{Number of GPS points per trip.}
\edafig{metadata_trips_by_hour}{Trips per hour of the day (local time).}
\edafig{polyline_max_speed}{Highest speed between two consecutive points in each trip.}
\edafig{polyline_map_hexbin}{Density of GPS points around Porto.}

\textbf{Cleaning.} We removed as little as possible:
\begin{itemize}
  \item For duplicate TRIP\_IDs we kept the copy with the most points. The
        other copies were almost always empty or only a few points long
        (81 rows removed).
  \item Trips with a point outside mainland Portugal were removed completely
        (32 trips). There were so few that repairing them was not worth it.
  \item Trips with fewer than 3 points are kept, because query 7 has to count
        them. They get \texttt{is\_valid = 0}, and the other queries filter
        them out.
  \item Trips with a GPS jump are kept and marked with \texttt{has\_gap = 1},
        so distance queries can leave them out.
  \item Empty ORIGIN\_CALL and ORIGIN\_STAND are stored as NULL.
\end{itemize}
After cleaning the database has \textbf{448 taxis, 1,710,557 trips and
83,408,413 GPS points}. Only 113 rows were removed in total.

\subsection*{Part 1 -- Schema}

We use four tables: \texttt{call\_type}, \texttt{taxi}, \texttt{trip} and
\texttt{gps\_point}. The most important choices were:
\begin{itemize}
  \item \texttt{trip} gets its own integer key, since TRIP\_ID is not unique
        in the raw data. A 4-byte key also saves about 320\,MB in
        \texttt{gps\_point}.
  \item Values we need often (start and end time, duration, distance,
        number of points, start and end point, bounding box) are computed
        once when loading. That way only query 6 has to read the 83 million
        GPS points.
  \item \texttt{gps\_point} is kept as small as possible: a composite primary
        key, no timestamp per point (it is \texttt{start\_time + 15 s $\cdot$ seq})
        and no extra indexes. The whole database is 3.3\,GB.
\end{itemize}

The loader (\texttt{insert\_data.py}) reads the CSV twice. The first pass
decides which rows to keep, and the second parses the trips in batches and
bulk-loads them with \texttt{LOAD DATA LOCAL INFILE}. The full load takes about
4 minutes. Afterwards we checked that the number of points matches
\texttt{SUM(n\_points)}, that there are no orphan rows, and that a few
trips match the CSV exactly.

\begin{lstlisting}[language=SQL]
CREATE TABLE call_type (
    code        CHAR(1)      NOT NULL,
    description VARCHAR(40)  NOT NULL,
    PRIMARY KEY (code)
);

CREATE TABLE taxi (
    taxi_id     INT UNSIGNED NOT NULL,
    PRIMARY KEY (taxi_id)
);

CREATE TABLE trip (
    id            INT UNSIGNED      NOT NULL AUTO_INCREMENT,
    trip_code     BIGINT UNSIGNED   NOT NULL,
    taxi_id       INT UNSIGNED      NOT NULL,
    call_type     CHAR(1)           NOT NULL,
    origin_call   INT UNSIGNED      NULL,
    origin_stand  SMALLINT UNSIGNED NULL,
    day_type      CHAR(1)           NOT NULL,
    missing_data  BOOLEAN           NOT NULL,
    start_unix    INT UNSIGNED      NOT NULL,
    start_time    DATETIME          NOT NULL,
    end_time      DATETIME          NOT NULL,
    duration_s    INT UNSIGNED      NOT NULL,
    n_points      SMALLINT UNSIGNED NOT NULL,
    is_valid      BOOLEAN AS (n_points >= 3) VIRTUAL,
    distance_km   DECIMAL(9,3)      NOT NULL,
    has_gap       BOOLEAN           NOT NULL DEFAULT 0,
    start_lat     DECIMAL(8,6)      NULL,
    start_lon     DECIMAL(9,6)      NULL,
    end_lat       DECIMAL(8,6)      NULL,
    end_lon       DECIMAL(9,6)      NULL,
    min_lat       DECIMAL(8,6)      NULL,
    max_lat       DECIMAL(8,6)      NULL,
    min_lon       DECIMAL(9,6)      NULL,
    max_lon       DECIMAL(9,6)      NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uq_trip_code (trip_code),
    KEY idx_trip_taxi_start (taxi_id, start_time),
    KEY idx_trip_call_type (call_type),
    CONSTRAINT fk_trip_taxi FOREIGN KEY (taxi_id)
        REFERENCES taxi (taxi_id) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT fk_trip_call_type FOREIGN KEY (call_type)
        REFERENCES call_type (code) ON DELETE RESTRICT ON UPDATE CASCADE,
    CONSTRAINT chk_trip_day_type CHECK (day_type IN ('A', 'B', 'C')),
    CONSTRAINT chk_trip_times    CHECK (end_time >= start_time)
);

CREATE TABLE gps_point (
    trip_id  INT UNSIGNED      NOT NULL,
    seq      SMALLINT UNSIGNED NOT NULL,
    lat      DECIMAL(8,6)      NOT NULL,
    lon      DECIMAL(9,6)      NOT NULL,
    PRIMARY KEY (trip_id, seq),
    CONSTRAINT fk_gps_point_trip FOREIGN KEY (trip_id)
        REFERENCES trip (id) ON DELETE CASCADE ON UPDATE CASCADE
);
\end{lstlisting}

\subsection*{Part 2 -- Queries}

The queries are in two Python programs, \texttt{queries/part2\_q1\_5.py} and
\texttt{queries/part2\_q6\_10.py}, built like \texttt{example.py} from the
assignment. Each program opens a connection through \texttt{DbConnector}
(\texttt{mysql-connector-python}, settings from a \texttt{.env} file), runs the
SQL for each task with \texttt{cursor.execute()} and reads the rows with
\texttt{cursor.fetchall()}. All answers are computed in MySQL. Python only
prints the results as tables with \texttt{tabulate}, does a few small counts
on the returned rows (for example how many circular trips hardly move in
Q9), and writes the full lists to \texttt{queries/output/}. Each program
prints its SQL before the result, so the screenshots show the query that was
run. One task can be run on its own, for example
\texttt{python queries/part2\_q6\_10.py 6}.

The two queries that do the most work are Q6 and Q10. Q6 first uses the
bounding box stored on each trip to skip trips that are nowhere near City
Hall, and then measures the distance from each remaining GPS point (inner
part of the query):
\begin{lstlisting}[language=SQL]
SELECT p.trip_id,
       MIN(ST_Distance_Sphere(POINT(p.lon, p.lat),
                              POINT(-8.62911, 41.15794))) AS min_dist_m
FROM trip t
JOIN gps_point p ON p.trip_id = t.id
WHERE t.min_lat <= 41.15794 + 0.0010 AND t.max_lat >= 41.15794 - 0.0010
  AND t.min_lon <= -8.62911 + 0.0013 AND t.max_lon >= -8.62911 - 0.0013
  AND p.lat BETWEEN 41.15794 - 0.0010 AND 41.15794 + 0.0010
  AND p.lon BETWEEN -8.62911 - 0.0013 AND -8.62911 + 0.0013
GROUP BY p.trip_id
HAVING min_dist_m <= 100;
\end{lstlisting}
Q10 uses the window function \texttt{LAG} to find the end of the previous
trip of the same taxi. The idle time is the start of a trip minus the end of
the previous one. The version below is shortened. The program also
computes the 8-hour variant and counts overlapping trips:
\begin{lstlisting}[language=SQL]
WITH ordered AS (
    SELECT taxi_id,
           CAST(start_unix AS SIGNED)
             - CAST(LAG(start_unix + duration_s)
                    OVER (PARTITION BY taxi_id ORDER BY start_unix, id)
               AS SIGNED) AS idle_s
    FROM trip
    WHERE is_valid = 1
)
SELECT taxi_id, ROUND(AVG(idle_s) / 3600, 2) AS avg_idle_h
FROM ordered
WHERE idle_s >= 0
GROUP BY taxi_id
ORDER BY avg_idle_h DESC
LIMIT 20;
\end{lstlisting}

\section*{Discussion}

\textbf{What we did differently.} The assignment does not say which timezone
to use. We chose local Porto time, because that is when the trips actually
happened. 157,929 trips (9\,\%) end up in a different time band than with
UTC, but the share of trips in each band changes by at most about one
percentage point in 4b.
We also could not use TRIP\_ID as the primary key, since it is not unique,
so \texttt{trip} got its own key.

\textbf{Invalid trips and GPS jumps.} We kept both and marked them instead
of deleting them. This way query 7 can count the invalid trips, and the
other queries can choose what to include. The downside is that every query
has to state which trips it uses. For distances the difference turned out to
be small, only 2--4\,\% in 4b.

\textbf{The flags in the dataset are not reliable.} DAY\_TYPE is always ``A''
and MISSING\_DATA marks only 10 trips, while about 38,000 trips clearly have
gaps. We therefore judged data quality from the trajectories themselves.

\textbf{Rankings per taxi.} Taxis with few or strange trips end up at the top
of some rankings. The top taxi in Q3 has 61\,\% invalid trips, and the two
highest values in Q10 come from taxis with only 4 and 25 trips. In Q10 we
define idle time as the next start minus the previous end. Without a limit,
days off dominate the average. If we only count breaks shorter than 8 hours,
the top 20 are between 85 and 106 minutes. We still use the plain average
as our main answer, since that is what the task asks for, and show the
8-hour variant next to it in the output.

\textbf{Limitations.} Query 6 only checks the GPS points, not the line
between them, so a taxi that passes City Hall between two points 15 seconds
apart can be missed.

\textbf{Pain points.} The main practical problem was the size of the data.
To keep the load time and disk use down with 83 million GPS points, we
bulk-loaded with \texttt{LOAD DATA}, turned off the binary log and kept
\texttt{gps\_point} as narrow as possible.

\textbf{What we learned.} We learned that it pays off to explore the data
properly before designing the schema. Both the duplicate IDs and the GPS
jumps would have caused problems if we had found them later. We also learned
how much schema choices such as key size and precomputed columns matter
when a table has tens of millions of rows.
